## Interpretation

1. **The DriveCommand reached the ESP32 and was accepted as fresh.**
   `command_fresh` went true while publishing and false within 1 s of stopping.
   Transport and freshness handling work.
2. **The brake-step PASS proves nothing.** `brake_active` is already true at
   idle, so a brake=True command reading true is not a transition. Brake-field
   decoding is therefore still unverified.
3. **Why steering stayed at 0 and brake stayed active is unknown.** There are
   two hypotheses, and the firmware findings doc must settle them. Do not guess
   between them:
   - **(a) Firmware inhibit while the VESC is unpowered.** The firmware may
     keep its failsafe outputs (brake + centred steering) whenever VESC
     telemetry is not fresh (`telemetry_fresh=false`, age 0xFFFFFFFF), even
     though the command itself is fresh. If so, this test's premise ("with the
     battery unplugged the ESP32 still updates its echo fields") is wrong for
     this firmware. A1b as written cannot pass on this build, and the format
     proof needs a different observable.
   - **(b) DriveCommand field mismatch between the Orin and the ESP32.** For
     example, a different field order or offset in what the flashed build
     decodes would make `steering_angle_rad` read as 0. This is less likely
     given the provenance note in `DriveCommand.msg`, but `requested_erpm=0`
     can't separate (a) from (b) while the VESC is unpowered.
   Separating them needs `esp32_installed_firmware_findings.md` (the gating
   conditions for `steering_target_rad` and `brake_active`), which is not in
   this repo.
