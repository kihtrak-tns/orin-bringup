1. **The servo command never moved.** `pca9685.steering_command_deg` stayed at
   100° (1611 µs) in a sample taken 2.9 s into commanding 0.1 rad (≈5.7°).
   So the firmware did not just skip reporting `steering_target_rad`: it did
   not act on the steering request at all. The "echo-only" explanation is ruled out.
2. **The only output that responds to DriveCommand is `command_fresh`.** It
   rises while commands arrive and falls within 1 s of silence, so micro-ROS
   delivers and deserializes *something* on `/laksa/command`. The DDS type
   name matched, or the subscription would never fire.
3. **`brake_active` is True in every state,** including while commanding
   brake=False. The brake field is still unverified in both directions.

## Hypotheses: none confirmed or ruled out by this run

- **(a) Firmware inhibits outputs while the VESC is unpowered/stale.** The
  results fit it ("everything inert except freshness"), but the operator
  reports that `esp32_installed_firmware_findings.md` documents no such
  failsafe. The only documented safeties are the 500 ms command timeout
  (→ brake + centre) and agent-disconnect (→ stop actuators). No source
  supports it.
- **(b) DriveCommand field/offset mismatch between the Orin and the flashed
  firmware.** This is **fully unverified**, and this run does not weaken it.
  A1a only checked the ESP32→Orin direction (VehicleState, VescState,
  Pca9685State), never the bytes the Orin publishes. A layout mismatch that
  still deserializes would produce exactly this: commands counted as fresh,
  with the steering/brake values not what was sent. The `.msg` provenance
  note is a claim about a source branch, not evidence of what the flashed
  build decodes.
- **(c) Unexplored: a separate brake latch driven by `/laksa/brake`
  (std_msgs/Bool).** laksa_esp32 subscribes to it (1 subscription, 0
  publishers during prep), and A1b never publishes it. If the firmware holds
  its outputs in brake+centre until an explicit `false` arrives there, every
  column above is explained. This is untested and undocumented, and testing
  it means publishing a command topic, which needs the same human gate.

## Ways to separate them (not done; each needs a decision)

- **(b), no hardware needed:** get the DriveCommand deserialization the
  flashed build actually compiled in (typesupport/`.msg` at the built commit,
  or strings/symbols from the flash image) and compare it field by field with
  `rclpy.serialization.serialize_message(DriveCommand(...))` on the Orin.
  That is the outbound counterpart of A1a's raw==typed check.
- **(c):** read how the firmware handles `/laksa/brake` (the source for its

  with the battery unplugged. It needs the operator's go-ahead and the

- **(a):** firmware source for what gates the steering/brake outputs, or the

- micro-ROS agent `-v6` during a run would show the byte length of the
