## 2. Launch file and parameters

The launch directory (listed, not guessed) has `sllidar_a2m12_launch .py`.
Upstream, the filename contains a **stray space before `.py`**. It is
invoked with the name quoted exactly. Defaults in that file: port
`/dev/ttyUSB0`, baud 256000, `frame_id=laser`, `angle_compensate=true`,
`scan_mode=Sensitivity`. The node's own built-in baud default is 1000000.

Invocation used, overriding port and baud explicitly:
```
ros2 launch sllidar_ros2 "sllidar_a2m12_launch .py" serial_port:=/dev/laksa_lidar serial_baudrate:=256000
```
`/dev/laksa_lidar -> ttyUSB0` (udev rule untouched).

Upstream quirk: this launch file declares `scan_mode` but never passes it to
the node. The driver picked **Sensitivity** anyway as the device default,
so the effect was the same.

## Why 12.8 Hz and not 10 Hz

In this driver commit, `scan_frequency` (default 10) is only used to size
the angle-compensation buffer and in the log line. The motor is started
with `setMotorSpeed()` with no argument, i.e. the device's default speed.
On this unit (firmware 1.32, hw rev 6) that default is ~12.8 Hz. So the
"scan frequency:10.0 Hz" log line is nominal, not the actual rate. The rate
is very stable (std dev ~2.5 ms), so this is not a fault.

## Note for mapping/nav tuning: sample rate vs angular density
Not a defect, just worth knowing. In Sensitivity mode the A2M12 samples at a
fixed **16 kHz**, so the scan rate trades directly against angular density:

| scan rate | samples / revolution | mean angular spacing |
|---|---|---|
| 12.8 Hz (current, device default) | ~1250 | ~0.29° |
| 10 Hz (plan nominal) | ~1600 | ~0.225° |

The published `/scan` still has 1800 bins, because the angle-compensation
grid in this driver commit is sized for a hardcoded 10 Hz. At 12.8 Hz, some
bins in each revolution get no sample and show as `inf`, which accounts for
part of the ~14% `inf` seen above. Anything that treats `inf` as "free space
to max range" or counts beams (scan matching, costmap raytracing) should keep
this in mind.

## Follow-up (documented, deliberately not done): make the scan rate configurable
This driver commit calls `setMotorSpeed()` with no argument, so it always
runs at the device default (12.8 Hz here). The SDK call does accept a speed
argument, so a variable rate is possible in principle. To make it a real
launch-time parameter, not just a different fixed number:
1. Patch the vendored node to accept a `scan_frequency` (or motor-speed)
   launch parameter and pass it into `setMotorSpeed()`.
2. Make `scan_frequency` actually size the angle-compensation buffer from
   the real rate, not a hardcoded 10 Hz.
3. Empirically find the safe/working speed range for THIS unit (firmware
   1.32, hw rev 6): try candidate values and check health, achieved Hz and
   data quality at each. Slamtec doesn't publish an exact adjustable range
   per model.

Deliberately not done tonight: this is trial-and-error on hardware and fits
better as a Phase D-style deliberate, one-change-at-a-time task than
something rushed late at night. Revisit when there's a concrete reason to
want a different rate (e.g. mapping/nav tuning in Phase D/E). This is
recorded here rather than in `orin_bringup_plan.md`'s "Still open" list
because the plan lives in the claude.ai project, not this repo. The cloud
Claude may want to mirror it there.
