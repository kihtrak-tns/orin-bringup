## Finding: the firmware ceiling C
- **Passed unchanged:** +1242, +2070 and −2070 eRPM. Requested and active matched 4140 × v
  within 1 eRPM, with no clamp.
- **4140 eRPM (1.00 m/s) is REJECTED, not clamped.** For about 0.5 s the ESP32 kept the previous
  2071. Then requested and active both dropped to 0 for the rest of the hold (CSV: 2071 until
  t = 0.49 s, 0 from t = 0.60 s). That is the firmware ignoring an out-of-range command, with its
  500 ms command watchdog then zeroing the output.
- **C lies between 2070 and 4140 eRPM (0.50 to 1.00 m/s).** A command above C does not get
  capped: it stops the drive.
- **Repo source vs installed firmware:** `firmware/esp32-s3/src/micro_ros_bridge.c`
  `speed_to_erpm()` returns false (rejects) above `VESC_MAX_ABS_RPM`, which `esp32_config.h`
  sets to **900**. The installed firmware accepted 2071, so its limit is higher than the repo's.
  This fits the known "installed firmware is an unmatched dirty build" finding, and the reject
  behaviour matches the source.

## Verdict
**GATE PASS — C recorded:** the installed firmware rejects (does not clamp) commands above a
limit C with 2070 < C < 4140 eRPM. It passes ±2070 eRPM unchanged.

**The firmware limit is not a constraint tonight.** Every cap planned for tonight is ≤ 1,000 eRPM
(0.22 m/s ≈ 911 eRPM), well inside the ±2070 eRPM already shown to pass unchanged. The supervisor
cap (`navigation_max_erpm`, `exploration_max_erpm`) is the effective ceiling.

Note for later phases: because the firmware rejects rather than clamps, a command above C does
not produce C. It produces a stop after about 0.5 s. Do not rely on the firmware as a speed limiter.
